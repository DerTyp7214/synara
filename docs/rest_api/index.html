Synara REST API

Services: RPC_SERVICES.md · Models: MODELS.md · Guide: CLIENT_REST.md · Index: README.md

How to read this file

  • Every route is derived from an RPC interface function; the derivation rules (method, path segment, parameter binding) are listed in How routes are derived below and explained with examples in CLIENT_REST.md.
  • Parameters lists each parameter with its binding: path (a path segment), query (a query parameter; collections repeat the name= pair, objects on GET are JSON-encoded) or body (JSON; when a route has several body parameters the request body is one JSON object with one field per parameter). optional marks a parameter that has a default or is nullable, and the text after the colon is its documentation.
  • Response is JSON <type> (a JSON body), SSE <item type> (Server-Sent Events, one JSON object per data: line), FILE (served on GET and HEAD with Accept-Ranges: bytes and Content-Disposition: inline), BYTES (a raw binary body) or - (an empty 200).
  • Auth is public (no token needed), JWT (an Authorization: Bearer <token> header or the synara-auth cookie), JWT + Admin or JWT + <CAPABILITY> for a required user capability.
  • The serverStats, auth, handshake services are mounted without requiring a user, so all of their routes are reachable without a token and are listed as public here.
  • Errors are returned as a plain-text body with status 400, 401, 403, 404 or 500.

How routes are derived

Nothing on this page is written by hand: every route below is derived from one function of an RPC service interface by the same rules the server's routing code is generated with.

Service prefix. The interface name without a leading I and a trailing Service, with the first letter lowercased: ISongService is mounted at /song, IPodcastService at /podcast.

Verb and path segment. They follow the function name. The first matching rule wins, and a prefix only matches as a whole word — the character after it must be an upper-case letter or a digit, or the name must be exactly the prefix. The segment keeps the name with its first letter lowercased.

Explicit overrides. @RestGet, @RestPost, @RestPut and @RestDelete on the function replace the derived verb; @RestPath("segment") replaces the derived segment.

Path parameters. A parameter named type that is primitive, not nullable and has no default becomes a leading {type} segment. The first parameter named id or ending in Id that is primitive, not nullable and has no default becomes a trailing {name} segment. Every other parameter binds by its type and the route's verb.

/clientSettings — IClientSettingsService

Stores the settings of the clients of a user as opaque key/value entries, where the value is an arbitrary JSON document in text form and the server never interprets what a setting means. Entries live either in the synced scope, which is shared by all devices of the user, or in the device scope of a single device, and the client decides per key which one it uses. Each scope carries a monotonically increasing version that every accepted write advances by one, and every entry remembers the version it was written at, so clients detect concurrent changes and can catch up incrementally instead of reading everything again.

/entityChange — IEntityChangeService

Answers which library entities changed since a time the client names, so a client that keeps library data reads only those again instead of everything. It is a pull the client starts and not a subscription. Every returned stream delivers the changes recorded so far and then completes, nothing is emitted afterwards. The live notifications are IChangeService.observeChanges. A result contains library changes plus the caller's own LIKE and TIMECODES changes, ordered by time. A filtered pull returns the changes of every object a client gets when it loads that artist, album, playlist or collection, including objects nested in others, such as the artists and the album of a song, the artists of an album and the member artists of an artist that is a group. A change is recorded once for the entity it happened to, so an object nested in several others is reported once as itself, and a client updates the copies it holds by id. A client calls IEntityChangeService.getWindow first, pulls with the time it kept from its last pull and keeps the new one for the next.
